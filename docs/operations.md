# 运维与恢复

## 异常中断

中断后先读取任务、证据和原生运行状态，再核对目标仓库的 Git 现场、相关差异、未跟踪文件和
旧执行进程。旧执行者未确认停止时不能接手。

运行结果未知时：

1. 检查实际副作用和已有成果。
2. 使用 `settle` 保存恢复依据与下一步。
3. 验证已有代码后，保持原任务和问题标识新建接续运行。
4. 不直接修改 Spec Kit 私有运行状态。

```sh
.venv/bin/python scripts/flow.py settle specs/<feature> <attempt> \
  --evidence '<需求内证据路径>' --reason '<恢复结论>'
```

历史失败、尝试次数和版本证据跨会话保留。未知结果不等于失败，也不等于通过。

## 单向通知

通知是可选的飞书单向提醒，仅覆盖“需要用户介入”和“整个需求开发完成”。通知失败不改变
业务状态，也不会自动重试已经处于发送中或未知状态的事件。

```sh
.venv/bin/python scripts/notify.py check
.venv/bin/python scripts/notify.py test --dry-run
```

真实测试会发送一条明确标识的消息。Webhook 无法验证实际群名，发送后需要人工确认目标和
机器人。

## 请求用户决定

```sh
.venv/bin/python scripts/flow.py request-decision specs/<feature> review \
  --key '<稳定问题标识>' --summary '<问题摘要>' --next '<所需决定>'
```

- 需求或 UI 澄清使用 `review`。
- 执行计划澄清使用 `plan`。
- 任务中的问题使用任务 ID，例如 `T001`。

命令会先保存待确认事项，再尝试发送提醒。正式评审和计划确认仍须在用户回复后通过
`approve` 保存。群内消息本身不构成批准。

相同需求和版本下的事件会去重。通知失败、未配置或投递结果未知时，业务工作仍在 Codex
会话中继续处理。

## 周报评分标准 v1

本口径用于评估已观察到的研发流程表现，不替代任务完成条件或验收状态。已有复盘按原有
安排使用；新项目不自动创建定时任务。真实样本、评分证据及业务周报保存在本地或组织批准
的系统，不上传个人框架仓库。

### 样本与证据

- 只使用本期新增、可追溯的真实业务执行证据，记录区间、证据截至时间、实际流程版本、
  生效变化和评分口径版本。多个流程版本分别说明，不混作同一配置的表现。
- 分别报告新增需求数、任务数和有效评估样本数，明确样本单位、阶段、类别、复杂度和影响
  范围。同一任务的多次运行、修复与检查不重复计数；旧样本的新证据只记本期增量。
- 隔离夹具、安装检查和框架单元测试不作真实业务效果样本。只比较同类任务，比例同时给出
  分子、分母及来源。样本少只提观察，不宣称提效或成本回报。
- 无新增有效真实业务样本时写「本期暂不评分」，说明样本情况与下一轮观察项；不打零分，
  不沿用上期总分。

### 五维评分

每项 0–2 分，逐项提供分值、理由、证据定位和局限。依据原生需求、任务、运行记录、测试
及当前代码版本判断，不仅凭聊天中的完成宣称给分。样本表现不一时说明正反例与覆盖范围。

| 维度 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- |
| 样本与证据 | 真实样本充分且同类可比，任务、阶段、代码版本与验证来源可追溯 | 有真实可追溯样本，但数量、可比性或覆盖不足 | 已有执行，但应有的关键记录缺失、失效或矛盾，核对后仍无有效证据支持判断 |
| 交付闭环 | 评估范围内的测试、必要独立检查和约定验收覆盖当前代码并闭环；阶段交付明确边界 | 部分验证通过，成果可核对，完整闭环尚未完成 | 交付正确性无法确认，或必要验证失败、遗漏，无法形成可信交付 |
| 效率与返工 | 同类任务在明确测试口径下首次通过，返工少，无明显重复或无效重试 | 有修复和复测，但复用了已有成果，无明显失控重复 | 明显重复工作、无效重试或反复丢弃已验证成果，影响推进 |
| 恢复可靠性 | 实际接续时定位任务、代码、副作用及旧执行者，安全复用成果，保留累计限制 | 能接续，但定位、证据或过程存在缺口，补核对后继续 | 接续状态仍不明，或存在重复执行、并行写入、副作用重放风险，无法安全接续 |
| 可观测性与人工负担 | 决定、测试、失败和接续可追溯，人工仅参与预定确认或必要业务决定，无执行救援 | 存在影响判断的未知或偶发人工救援，处理仍可追溯 | 失败难追溯，或频繁依赖用户执行救援 |

### 未知项与汇总

- 区分未触发、信息不可得和已观察到失败。未触发恢复时写「无法评估：本期未触发」，
  不扣分也不给满分。其他无法判断的维度同样标明原因；已确认应有证据缺失或失效才按
  相应零分锚点处理，无新增样本本身不属于失败。
- 预定确认、必要业务澄清、需求变更、等待接口和执行救援分开呈现。等待用户或接口不计为
  活跃执行耗时，不据此扣效率分。待联调不等于已验收，阶段通过不等于父需求完成。
- 实际下游模型、用量、耗时不可得时标记未知，说明其对判断的影响，不猜型号或推算费用、
  token 节省。
- 五项均可给分才相加为 0–10 分。有无法评估项时写「暂不汇总」，可展示已评估项分值，
  不补零、不折算成十分制、不套总分分档。
- 每期报告低、中或高置信度及理由，依据样本数、可比性、证据完整性和覆盖范围判断。
  样本少或关键能力未触发时明确局限；完整总分也不表示全部场景已验证。

| 总分 | 分档 |
| --- | --- |
| 9–10 | 健康 |
| 7–8 | 稳定 |
| 5–6 | 有明确改进空间 |
| 3–4 | 影响交付需调整 |
| 0–2 | 应先修复基础问题 |

越权修改、跳过必要验收或关键证据失效等严重事件，经核对事实、影响与来源后，可将总分
封顶 3 分。保留各项原始分、原始总分、是否封顶、最终分数和依据；原始总分低于 3 时不
抬高。存在无法评估项时仍不汇总，单列严重事件及处置建议，不为应用封顶而编造总分。

首次试评或低置信度示例不作为固定基线，也不重复计入新增样本。只有口径和证据可比时才
讨论分数升降。

### 周报输出

沿用已有周报，至少包含版本、区间与样本数，五维分值或无法评估原因、逐项证据、总分
及分档或不汇总原因、置信度和局限。说明已验证与未闭环部分、返工与恢复、模型适配和
检查发现；单列人工节点、等待接口、执行救援及严重事件。最多提出三项有证据的建议，
并列出下一轮观察项。评分本身不授权启动业务任务或修改流程、模型及自动化配置。
